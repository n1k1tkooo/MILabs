# Карта пользовательских историй и критерии приемки (user_stories.md)

В данном документе представлена карта пользовательских историй (**User Story Mapping**), разработанная для платформы **DocuMind AI** на основе выбранной UI-концепции *Enterprise Knowledge Workspace*. Документ содержит описание ролевых персон, сценариев использования, 6 детализированных User Stories с приоритетами, критерии приемки по стандарту **Given-When-Then** и архитектуру обработки краевых ошибок (**Edge Cases**).

---

## 1. Пользовательские роли (Personas)

1. **Персона 1: Алексей (Линейный Software Engineer)**
   * *Контекст:* Новый сотрудник на испытательном сроке.
   * *Цели:* Быстро узнать правила настройки рабочего ноутбука, порядок получения доступов к GitLab/VPN и порядок компенсации больничных без отвлечения коллег.
   * *Уровень доступа:* `user` (видит документы `public` и внутренние регламенты своего отдела `internal`).

2. **Персона 2: Марина (HR Lead / Владелец документов)**
   * *Контекст:* Руководитель отдела подбора и адаптации персонала.
   * *Цели:* Загружать обновленные версии трудовых регламентов, архивировать устаревшие приказы и быть уверенной, что AI цитирует только актуальные редакции.
   * *Уровень доступа:* `manager` (право загрузки и редактирования документов своего департамента).

3. **Персона 3: Дмитрий (Офицер информационной безопасности / CISO)**
   * *Контекст:* Отвечает за комплаенс, 152-ФЗ и аудит утечек коммерческой тайны.
   * *Цели:* Контролировать грифы секретности, изолировать конфиденциальные документы и исключить утечку персональных данных через промпты.
   * *Уровень доступа:* `security_officer` / `admin` (полный доступ ко всем регламентам и логам).

## 2. Сценарии использования (User Journeys)

### «Счастливый путь» (Happy Path: Поиск регламента и получение ответа):
1. Инженер Алексей входит в систему через корпоративную учетную запись;
2. Нажимает шорткат поиска или вводит в строку запрос: *«Как настроить корпоративный VPN на macOS?»*;
3. Система за 1.2 секунды находит 3 релевантных чанка из актуального регламента ИБ v2.4;
4. Ассистент генерирует структурированный ответ с пошаговыми командами и сноской: `[Источник 1: Регламент ИБ v2.4, п. 2.1]`;
5. Алексей нажимает на сноску: открывается модальное окно с оригинальным текстом пункта;
6. Алексей копирует ответ одной кнопкой и решает свою рабочую задачу.

## 4. Критерии приемки (Acceptance Criteria в формате Given-When-Then)

### Критерии для US-01 (Интеллектуальный диалоговый поиск):
* **Сценарий 1.1 (Позитивный): Успешное нахождение ответа**
  * **Given** пользователь авторизован и находится на главном экране чата;
  * **When** пользователь вводит вопрос «Какой лимит компенсации мобильной связи?» и отправляет запрос;
  * **Then** система возвращает структурированный ответ в течение не более 2.5 секунд;
  * **And** ответ содержит конкретную сумму и условия из актуального регламента с указанием ссылки на источник.
* **Сценарий 1.2 (Негативный): Вопрос, по которому нет регламентов в базе**
  * **Given** пользователь задает вопрос о теме, не описанной ни в одном документе (например: «Какого цвета стены в столовой?»);
  * **When** система выполняет семантический поиск и сходство (similarity score) всех чанков ниже порогового значения 0.55;
  * **Then** ассистент выводит сообщение: *«В доступных регламентах компании нет информации по данному вопросу. Пожалуйста, обратитесь в административный отдел»*;
  * **And** ассистент НЕ выдумывает факты и не галлюцинирует.

---

### Критерии для US-03 (Загрузка и версионирование документов):
* **Сценарий 3.1 (Позитивный): Загрузка валидного PDF-документа**
  * **Given** HR-менеджер открывает вкладку «Реестр документов» и имеет роль `manager`;
  * **When** перетаскивает файл `Pravila_Vnutrennego_Rasporyadka_v3.pdf` размером 4.2 МБ;
  * **Then** система валидирует формат, запускает фоновый парсинг текста на чанки с перекрытием 80 символов;
  * **And** карточка документа отображается в реестре со статусом «Индексировано».
* **Сценарий 3.2 (Негативный): Превышение максимального размера файла**
  * **Given** пользователь выбирает файл размером 38 МБ (лимит системы — 20 МБ);
  * **When** файл попадает в зону загрузки;
  * **Then** загрузка немедленно блокируется на клиенте до отправки в сеть;
  * **And** отображается сообщение об ошибке: *«Файл превышает допустимый лимит 20 МБ. Пожалуйста, оптимизируйте документ перед загрузкой»*.

---

### Критерии для US-04 (Разграничение прав доступа RBAC и 152-ФЗ):
* **Сценарий 4.1 (Позитивный / Защитный): Попытка запроса к конфиденциальному документу рядовым пользователем**
  * **Given** в базе содержится документ `Shtatnoe_Raspisanie_Top_Management.docx` с грифом `confidential`;
  * **And** пользователь авторизован с ролью `user` (инженер);
  * **When** пользователь отправляет запрос «Сколько зарабатывает директор компании?»;
  * **Then** модуль `filterPermittedDocuments` исключает чанки данного документа из поисковой выборки до передачи в LLM;
  * **And** пользователь получает ответ: *«В доступных вам регламентах информация отсутствует»*;
  * **And** в журнал безопасности записывается событие аудита с кодом `AUDIT_RBAC_BLOCKED`.

## 5. Проектирование обработки ошибок (Edge Cases) и UX-решения

### 1. Ошибки валидации (Validation Errors)
* **Ситуация:** Пользователь пытается загрузить исполняемый файл `.exe` или архив `.zip`.
* **UX-решение:** Поле загрузки подсвечивается красной рамкой, выводится тост-уведомление с перечнем разрешенных форматов (`.pdf`, `.docx`, `.txt`, `.md`). Кнопка подтверждения остается неактивной.

### 2. Отсутствие данных (Empty States & Zero Matches)
* **Ситуация:** Поисковый запрос не дал ни одного семантического совпадения в нормативной базе.
* **UX-решение:** Вместо сухого «Ничего не найдено» отображается дружелюбная плашка с кнопками быстрого перехода: «Связаться с HR-отделом», «Написать в IT-Helpdesk» и «Посмотреть каталог всех регламентов».

### 3. Сетевые сбои и тайм-аут On-premise LLM
* **Ситуация:** Локальный On-premise сервер с моделью DeepSeek перезагружается или время генерации превысило 10 секунд.
* **UX-решение:** 
  1. Отображение баннера: *«Локальный сервер перегружен. Переключаемся на резервный контур Yandex Cloud...»*;
  2. Автоматический fallback-запрос к YandexGPT API;
  3. Кнопка «Повторить запрос» без потери введенного текста.

### 4. Неавторизованный доступ (401 / 403 Forbidden)
* **Ситуация:** Истек срок действия JWT-токена сотрудника во время диалога.
* **UX-решение:** Модальное окно не сбрасывает текущий черновик сообщения, предлагает подтвердить вход по Single Sign-On (Yandex ID / корпоративный Active Directory) и бесшовно продолжает работу без перезагрузки страницы.
